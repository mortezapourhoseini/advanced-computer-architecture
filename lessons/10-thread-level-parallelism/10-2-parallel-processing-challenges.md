## ۱. دو مانع اصلی

کاربرد چندپردازنده از اجرای کارهای مستقل بدون هیچ ارتباطی تا اجرای برنامه‌های موازی با ارتباط زیاد بین نخ‌ها را در بر می‌گیرد. دو مانع مهم پردازش موازی را سخت می‌کنند و هر دو با **قانون امدال** توضیح داده می‌شوند:

- ۱. **موازی‌سازی محدود** در برنامه‌ها.
- ۲. **هزینه‌ی بالای ارتباط** بین پردازنده‌ها.

میزان سختی هر مانع هم به برنامه بستگی دارد و هم به معماری.

## ۲. مانع اول: موازی‌سازی محدود

قانون امدال (بخش ۱):

```math
\text{Speedup} = \frac{1}{\dfrac{F_{\text{enhanced}}}{S_{\text{enhanced}}} + (1 - F_{\text{enhanced}})}
```

برای چندپردازنده یک ساده‌سازی می‌کنیم: برنامه فقط دو حالت دارد:

- **حالت موازی** که همه‌ی پردازنده‌ها کاملاً مشغول‌اند (حالت بهبودیافته با سرعت‌افزایی n).
- **حالت ترتیبی** که فقط یک پردازنده کار می‌کند.

```math
\text{Speedup}(n) = \frac{1}{\dfrac{F_{\text{parallel}}}{n} + (1 - F_{\text{parallel}})}
```

## ۳. مثال کتاب: سرعت‌افزایی ۸۰ با ۱۰۰ پردازنده

**صورت:** می‌خواهیم با ۱۰۰ پردازنده سرعت‌افزایی ۸۰ بگیریم. چه کسری از محاسبه‌ی اصلی می‌تواند ترتیبی باشد؟

**حل:**

```math
80 = \frac{1}{\dfrac{F}{100} + (1 - F)} \quad\Rightarrow\quad 0.8F + 80(1 - F) = 1 \quad\Rightarrow\quad 80 - 79.2F = 1
```

```math
F = \frac{79}{79.2} = 0.9975
```

پس فقط **۰.۲۵٪** محاسبه‌ی اصلی می‌تواند ترتیبی باشد! برای سرعت‌افزایی خطی (n با n پردازنده) معمولاً کل برنامه باید موازی باشد. در عمل برنامه‌ها فقط دو حالت ندارند و در حالت موازی هم اغلب از همه‌ی پردازنده‌ها استفاده نمی‌کنند، پس وضع بدتر است.

```text
Speedup with 100 processors vs. parallel fraction:
F = 0.90   ->  9.2
F = 0.99   -> 50.3
F = 0.999  -> 91.0
```

## ۴. مانع دوم: تأخیر ارتباط دور

در چندپردازنده‌های حافظه‌مشترک موجود (زمان کتاب):

- **بین هسته‌های یک تراشه:** ارتباط داده حدود ۳۵ تا ۵۰ سیکل.
- **بین هسته‌های تراشه‌های جدا:** از ۱۰۰ سیکل تا ۵۰۰ سیکل یا بیشتر در چندپردازنده‌های بزرگ.

این عدد به سازوکار ارتباط، نوع شبکه و مقیاس سیستم بستگی دارد.

## ۵. مثال کتاب: هزینه‌ی ارجاع دور

**صورت:** برنامه‌ای روی یک چندپردازنده‌ی ۳۲ پردازنده‌ای اجرا می‌شود. رسیدگی به ارجاع به حافظه‌ی دور ۲۰۰ نانوثانیه طول می‌کشد. فرض کن همه‌ی ارجاع‌ها جز ارجاع‌های ارتباطی در سلسله‌مراتب حافظه‌ی محلی اصابت دارند (فرضی کمی خوش‌بینانه). پردازنده روی درخواست دور متوقف می‌شود و فرکانس ۳.۳ گیگاهرتز است. اگر CPI پایه (همه‌ی ارجاع‌ها اصابت) ۰.۵ باشد، چندپردازنده بدون ارتباط چقدر سریع‌تر از حالتی است که ۰.۲٪ دستورها ارجاع دور دارند؟

**حل:**

```math
\text{CPI} = \text{Base CPI} + \text{Remote request rate} \times \text{Remote request cost}
```

```math
\text{Remote request cost} = \frac{200 \text{ ns}}{0.3 \text{ ns}} \approx 666 \text{ cycles}
```

```math
\text{CPI} = 0.5 + 0.002 \times 666 = 0.5 + 1.33 = 1.83
```

پس چندپردازنده با ارجاع‌های کاملاً محلی **1.83 / 0.5 ≈ 3.7 برابر** سریع‌تر است. یعنی فقط ۰.۲٪ دستورها (دو دستور از هر هزار) کارایی را تقریباً به یک چهارم می‌رساند.

> **اختلاف با کتاب:** کتاب حاصل‌ضرب 0.2% × 666 را **1.2** نوشته و نتیجه‌ی CPI = 1.7 و نسبت 3.4 را گرفته است. حساب درست 0.002 × 666 = 1.33 است، پس CPI = 1.83 و نسبت حدود 3.7 درست است. پیام مثال تغییر نمی‌کند.

تحلیل واقعی پیچیده‌تر است: بخشی از ارجاع‌های غیرارتباطی هم در سلسله‌مراتب محلی عدم اصابت دارند، و هزینه‌ی ارجاع دور ثابت نیست. رقابت روی شبکه‌ی سراسری می‌تواند تأخیر را خیلی بیشتر کند.

## ۶. راه‌های مقابله

| مشکل | راه‌حل نرم‌افزاری | راه‌حل سخت‌افزاری |
|---|---|---|
| موازی‌سازی ناکافی | الگوریتم‌های موازی جدید؛ نرم‌افزاری که زمان کار با همه‌ی پردازنده‌ها را بیشینه کند | کمک محدود؛ عمدتاً مشکل نرم‌افزار است |
| تأخیر ارتباط دور (کم کردن تعداد) | بازسازی داده تا دسترسی‌ها محلی شوند | کش کردن داده‌ی مشترک (جلسه‌های ۳ تا ۹) |
| تأخیر ارتباط دور (تحمل کردن) | پیش‌واکشی نرم‌افزاری | چندنخنگی، پیش‌واکشی سخت‌افزاری، مدل‌های سازگاری آزاد (جلسه‌ی ۱۳) |

بخش بزرگی از این فصل درباره‌ی کاهش اثر تأخیر ارتباط است: کش کردن داده‌ی مشترک در حالی که دید منسجم از حافظه حفظ شود (انسجام کش)، و همگام‌سازی که ذاتاً ارتباط بین پردازنده‌هاست و موازی‌سازی را محدود می‌کند.

## ۷. سرعت‌افزایی، بازده و دو نوع مقیاس‌پذیری

**بازده سرعت‌افزایی (speedup efficiency):**

```math
\text{Efficiency} = \frac{\text{Speedup}(n)}{n}
```

مثلاً اگر ۴ هسته سرعت‌افزایی ۳ بدهند، بازده ۷۵٪ است. در جلسه‌ی ۱۴ می‌بینیم که روی Core i7 محک‌های PARSEC بازده ۷۶٪ و محک‌های جاوا ۶۷٪ روی چهار هسته داشتند.

دو روش برای اندازه‌گیری مقیاس‌پذیری:

- **مقیاس‌پذیری قوی (strong scaling):** اندازه‌ی مسئله **ثابت** است و تعداد پردازنده زیاد می‌شود. قانون امدال دقیقاً این حالت را توصیف می‌کند.
- **مقیاس‌پذیری ضعیف (weak scaling یا scaled speedup):** اندازه‌ی مسئله **همراه با** تعداد پردازنده بزرگ می‌شود. اگر بخش ترتیبی ثابت بماند و بخش موازی بزرگ شود، سرعت‌افزایی نزدیک خطی می‌ماند.

```math
\text{Scaled speedup} = (1 - F) + F \times n
```

این فرمول (که به قانون گوستافسون معروف است) با فرض این است که روی n پردازنده، کسر زمان ترتیبی (1 - F) باشد. در جلسه‌ی ۱۴ باوری را می‌بینیم که با همین روش ادعا کرد «قانون امدال شکسته شد»، و توضیح می‌دهیم چرا گمراه‌کننده بود.

## ۸. آزمایش عملی: جمع موازی با OpenMP

این آزمایش روی یک سرور مجازی Xeon با **دو هسته** اجرا شد. برنامه مجموع مربع‌های ۶۴ میلیون عدد دقت مضاعف را ۱۰ بار حساب می‌کند:

```c
#include <omp.h>
#include <stdio.h>
#include <stdlib.h>
#define N (1L << 26)
int main(void) {
    double *a = malloc(N * sizeof(double));
    for (long i = 0; i < N; i++) a[i] = 1.0 / (i + 1);
    for (int t = 1; t <= 2; t++) {
        omp_set_num_threads(t);
        double s = 0, t0 = omp_get_wtime();
        for (int r = 0; r < 10; r++) {
            s = 0;
            #pragma omp parallel for reduction(+:s)
            for (long i = 0; i < N; i++) s += a[i] * a[i];
        }
        printf("%d thread(s): %.3f s  (s = %.6f)\n", t, omp_get_wtime() - t0, s);
    }
    return 0;
}
```

کامپایل با `gcc -O2 -fopenmp psum.c`. نتیجه:

| تعداد نخ | زمان (ثانیه) | سرعت‌افزایی | بازده |
|---|---|---|---|
| یک نخ | ۰.۷۷ | ۱ | ۱۰۰٪ |
| دو نخ | ۰.۴۱ تا ۰.۴۳ | حدود ۱.۸ | حدود ۹۰٪ |

نکته‌ها:

- **عبارت `reduction(+:s)`** همان تبدیل کاهش جلسه‌ی ۹-۱۴ است: هر نخ مجموع جزئی خودش را دارد و در پایان جمع می‌شوند.
- **چرا ۲ نیست؟** بخش ترتیبی کوچک (ساخت نخ‌ها، ترکیب مجموع‌ها) و مهم‌تر از آن **پهنای باند حافظه‌ی مشترک**: آرایه ۵۱۲ مگابایت است و از DRAM می‌آید، و دو هسته پهنای باند حافظه را تقسیم می‌کنند. با هسته‌ی بیشتر، این اثر بزرگ‌تر می‌شود (مدل Roofline جلسه‌ی ۹-۹).
- **اگر بدون `reduction`** بنویسی و همه‌ی نخ‌ها مستقیم به `s` اضافه کنند، هم جواب غلط می‌شود (جلسه‌ی ۱۰) و هم کندتر (جلسه‌ی ۷).

## ۹. تمرین‌ها

<details><summary>تمرین ۱: کسر موازی لازم</summary>

**صورت:** برای سرعت‌افزایی ۵۰ با ۶۴ پردازنده، کسر موازی حداقل چقدر باید باشد؟

**جواب:** 50 = 1 / (F/64 + 1 - F). پس F/64 + 1 - F = 0.02، یعنی F × (1 - 1/64) = 0.98 و F = 0.98 / 0.984375 ≈ 0.9956. یعنی حداکثر ۰.۴۴٪ ترتیبی.
</details>

<details><summary>تمرین ۲: حد سرعت‌افزایی</summary>

**صورت:** اگر ۵٪ برنامه ترتیبی باشد، حداکثر سرعت‌افزایی با بی‌نهایت پردازنده چقدر است؟ با ۱۶ پردازنده چطور؟

**جواب:** با بی‌نهایت پردازنده 1 / 0.05 = 20. با ۱۶ پردازنده 1 / (0.95/16 + 0.05) = 1 / 0.109 ≈ 9.1.
</details>

<details><summary>تمرین ۳: ارجاع دور با نرخ متفاوت</summary>

**صورت:** در مثال بخش ۵، اگر نرخ ارجاع دور ۰.۰۵٪ باشد و هزینه‌ی هر ارجاع ۴۰۰ نانوثانیه (با فرکانس ۳.۳ گیگاهرتز)، CPI و نسبت کندی چقدر است؟

**جواب:** هزینه 400 / 0.3 ≈ 1333 سیکل. مقدار CPI = 0.5 + 0.0005 × 1333 ≈ 0.5 + 0.67 = 1.17. نسبت کندی 1.17 / 0.5 ≈ 2.3.
</details>

<details><summary>تمرین ۴: مقیاس قوی و ضعیف</summary>

**صورت:** برنامه‌ای روی یک پردازنده ۱۰٪ ترتیبی است. با ۱۰۰ پردازنده، سرعت‌افزایی قوی و سرعت‌افزایی مقیاس‌شده (با فرض اینکه روی ۱۰۰ پردازنده هم ۱۰٪ زمان ترتیبی باشد) را حساب کن.

**جواب:** قوی: 1 / (0.9/100 + 0.1) ≈ 9.2. مقیاس‌شده: 0.1 + 0.9 × 100 = 90.1. اختلاف بزرگ نشان می‌دهد چرا باید همیشه نوع مقیاس‌پذیری را گزارش کرد.
</details>
