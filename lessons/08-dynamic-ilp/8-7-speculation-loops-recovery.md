## ۱. حلقه با گمانه‌زنی

حلقه‌ی جلسه‌ی ۸-۴ را دوباره در نظر بگیر:

```asm
Loop:   L.D     F0,0(R1)
        MUL.D   F4,F0,F2
        S.D     F4,0(R1)
        DADDIU  R1,R1,#-8
        BNE     R1,R2,Loop      ; branches if R1 != R2
```

فرض کتاب: همه‌ی دستورات دو تکرار صادر شده‌اند. `L.D` و `MUL.D` تکرار اول نهایی شده‌اند و بقیه‌ی دستورات اجرایشان تمام شده. برای سادگی، آدرس ذخیره هنگام صدور حساب شده فرض می‌شود.

| خانه | Busy | دستور | وضعیت | مقصد | مقدار |
|---|---|---|---|---|---|
| خانه‌ی 1 | No | `L.D F0,0(R1)` | Commit | F0 | Mem[0 + Regs[R1]] |
| خانه‌ی 2 | No | `MUL.D F4,F0,F2` | Commit | F4 | #1 × Regs[F2] |
| خانه‌ی 3 | Yes | `S.D F4,0(R1)` | Write result | 0 + Regs[R1] | #2 |
| خانه‌ی 4 | Yes | `DADDIU R1,R1,#-8` | Write result | R1 | Regs[R1] − 8 |
| خانه‌ی 5 | Yes | `BNE R1,R2,Loop` | Write result | | |
| خانه‌ی 6 | Yes | `L.D F0,0(R1)` | Write result | F0 | Mem[#4] |
| خانه‌ی 7 | Yes | `MUL.D F4,F0,F2` | Write result | F4 | #6 × Regs[F2] |
| خانه‌ی 8 | Yes | `S.D F4,0(R1)` | Write result | 0 + #4 | #7 |
| خانه‌ی 9 | Yes | `DADDIU R1,R1,#-8` | Write result | R1 | #4 − 8 |
| خانه‌ی 10 | Yes | `BNE R1,R2,Loop` | Write result | | |

| فیلد | F0 | F2 | F4 |
|---|---|---|---|
| شماره‌ی ROB | 6 | | 7 |
| مشغول | Yes | No | Yes |

چند نکته:

- **مقصد ذخیره‌ها آدرس حافظه است:** خانه‌ی ۳ به آدرس 0 + Regs[R1] و خانه‌ی ۸ به 0 + #4 (یعنی R1 جدید از خانه‌ی ۴) می‌نویسد.
- **بارگذاری تکرار دوم از ROB استفاده کرده:** آدرسش Mem[#4] است، یعنی از مقدار R1 که هنوز در ROB است (هنوز نهایی نشده).
- **هیچ ایستگاه رزروی مشغول نیست:** همه‌ی اجراها تمام شده و فقط نهایی‌سازی مانده.
- **حافظه هنوز دست نخورده:** هیچ‌کدام از دو ذخیره هنوز حافظه را ننوشته‌اند، چون نهایی نشده‌اند.

## ۲. بازیابی از پیش‌بینی غلط

چون نه ثبات‌ها و نه حافظه تا نهایی‌سازی نوشته نمی‌شوند، خنثی کردن اثر گمانه‌زنی ساده است. فرض کن پرش خانه‌ی ۵ در واقع **انجام‌نشده** بوده (حلقه باید تمام می‌شد):

1. **دستورات قبل از پرش** (خانه‌های ۳ و ۴) وقتی به سر ROB برسند، عادی نهایی می‌شوند.
2. **وقتی پرش به سر ROB می‌رسد،** پیش‌بینی غلطش آشکار می‌شود. ROB پاک می‌شود (خانه‌های ۶ تا ۱۰ دور ریخته می‌شوند).
3. **واکشی از مسیر درست** (دستور بعد از پرش) دوباره شروع می‌شود.

```mermaid
flowchart LR
    H["ROB head: entries 3, 4 commit normally"] --> B["Entry 5: mispredicted branch reaches the head"]
    B --> F["Flush entries 6 to 10 and the register status"]
    F --> R["Restart fetch at the correct successor of the branch"]
```

**بازیابی زودهنگام:** در عمل، پردازنده‌های گمانه‌زن تا رسیدن پرش به سر ROB صبر نمی‌کنند. به محض اینکه پرش اجرا شد و پیش‌بینی غلطش معلوم شد، فقط خانه‌های **بعد از** پرش پاک می‌شوند، خانه‌های قبل از آن ادامه می‌دهند، و واکشی از مسیر درست شروع می‌شود.

کتاب نتیجه می‌گیرد: در پردازنده‌ی گمانه‌زن، کارایی **حساس‌تر** به پیش‌بینی پرش است، چون اثر هر پیش‌بینی غلط بیشتر است (کار بیشتری دور ریخته می‌شود). پس همه‌ی جنبه‌های پرش مهم‌تر می‌شوند: دقت پیش‌بینی، تأخیر تشخیص پیش‌بینی غلط و زمان بازیابی.

## ۳. استثنا در دستورات گمانه‌ای

قاعده: استثنا **تا وقتی دستور آماده‌ی نهایی‌سازی نشده، شناسایی نمی‌شود**.

- **دستور گمانه‌ای استثنا می‌دهد:** استثنا فقط **در ROB ثبت** می‌شود.
- **پرش قبلی اشتباه پیش‌بینی شده بود:** دستور نباید اجرا می‌شد. استثنا همراه با دستور هنگام پاک شدن ROB دور ریخته می‌شود و هرگز رخ نمی‌دهد.
- **دستور به سر ROB رسید:** حالا مطمئنیم که گمانه‌ای نیست و استثنا واقعاً گرفته می‌شود.

این همان حفظ رفتار استثنای جلسه‌ی ۷-۱ است، این بار با سخت‌افزار. مقایسه با روش‌های نرم‌افزاری جلسه‌ی ۷-۷ (بیت مسموم، دستور بررسی): اینجا نه کد اضافه لازم است و نه کامپایلر باید چیزی بداند.

## ۴. الگوریتم دقیق با ROB

شکل ۳.۱۴ کتاب، به شکل خلاصه. h خانه‌ی سر ROB، b خانه‌ی تخصیص‌یافته و r ایستگاه رزرو است:

```text
Issue (all)         wait until: reservation station r and ROB entry b both free
    for each source s in {rs, rt}:
        if (RegisterStat[s].Busy) {            // an in-flight instruction writes s
            h = RegisterStat[s].Reorder
            if (ROB[h].Ready) { RS[r].V = ROB[h].Value; RS[r].Q = 0 }   // value already in ROB
            else RS[r].Q = h                                             // wait for ROB entry h
        } else { RS[r].V = Regs[s]; RS[r].Q = 0 }
    RS[r].Busy = yes; RS[r].Dest = b
    ROB[b].Instruction = opcode; ROB[b].Ready = no
    FP op or load: RegisterStat[rd].Reorder = b; RegisterStat[rd].Busy = yes; ROB[b].Dest = rd
    load or store:  RS[r].A = imm

Execute, FP op      wait until: Qj == 0 and Qk == 0           compute result
Execute, load 1     wait until: Qj == 0 and no earlier stores in the queue    A = Vj + A
Execute, load 2     wait until: step 1 done and all earlier stores in ROB have a different address
                    read Mem[A]
Execute, store      wait until: Qj == 0 and store at queue head  ROB[h].Address = Vj + A

Write result (not store)   wait until: execution done and CDB available
    b = RS[r].Dest; RS[r].Busy = no
    broadcast result with tag b to all RS (replace matching Qj, Qk)
    ROB[b].Value = result; ROB[b].Ready = yes
Write result (store)       wait until: execution done and Qk == 0
    ROB[h].Value = RS[r].Vk

Commit              wait until: instruction at ROB head h and ROB[h].Ready
    if branch:  if mispredicted { clear ROB and RegisterStat; fetch from branch destination }
    else if store: Mem[ROB[h].Destination] = ROB[h].Value
    else: Regs[ROB[h].Dest] = ROB[h].Value
    ROB[h].Busy = no
    if (RegisterStat[d].Reorder == h) RegisterStat[d].Busy = no   // no later writer of d
```

مقایسه با الگوریتم توماسولو (جلسه‌ی ۸-۳) نشان می‌دهد گمانه‌زنی کنترل را به‌طور قابل توجهی پیچیده‌تر می‌کند. این شکل حالت ساده را نشان می‌دهد که پیش‌بینی غلط تا نهایی‌سازی حل نمی‌شود.

دو نکته‌ی ظریف:

- **منبع عملوند سه جا دارد:** فایل ثبات (اگر کسی در جریان نیست)، ROB (اگر نویسنده تمام کرده ولی نهایی نشده)، یا CDB در آینده (اگر نویسنده هنوز در حال اجراست).
- **آخرین خط نهایی‌سازی:** اگر بعد از این دستور، دستور دیگری همان ثبات را مقصد گرفته، فیلد وضعیت ثبات به آن دستور جدیدتر اشاره می‌کند و نباید پاک شود.

## ۵. ذخیره‌ها در پردازنده‌ی گمانه‌زن

| ویژگی | توماسولو | با گمانه‌زنی |
|---|---|---|
| کی حافظه نوشته می‌شود | در مرحله‌ی نوشتن نتیجه، وقتی آدرس و مقدار آماده‌اند | **فقط در نهایی‌سازی**، وقتی ذخیره به سر ROB رسیده |
| دلیل | | حافظه تا وقتی دستور گمانه‌ای است نباید عوض شود |

شکل الگوریتم یک ساده‌سازی دارد: ذخیره در مرحله‌ی نوشتن نتیجه منتظر مقدارش می‌ماند. در واقعیت، مقدار ذخیره فقط باید تا درست پیش از نهایی‌سازی برسد و سخت‌افزار می‌تواند آن را مستقیماً از دستور تولیدکننده در خانه‌ی ROB ذخیره قرار دهد. کتاب در مثال‌هایش اجازه می‌دهد ذخیره از مرحله‌ی نوشتن نتیجه رد شود و فقط در نهایی‌سازی منتظر آماده بودن مقدار بماند.

## ۶. مخاطره‌های حافظه با گمانه‌زنی

- **مخاطره‌های WAW و WAR از راه حافظه:** به‌طور خودکار حذف می‌شوند، چون حافظه فقط در نهایی‌سازی و **به ترتیب** نوشته می‌شود. وقتی یک ذخیره در سر ROB است، هیچ بارگذاری یا ذخیره‌ی قبلی‌ای در جریان نیست.
- **مخاطره‌ی RAW از راه حافظه:** با دو محدودیت حفظ می‌شود:
    1. یک بارگذاری مرحله‌ی دوم اجرایش (خواندن حافظه) را شروع نمی‌کند، اگر یک خانه‌ی فعال ROB که ذخیره است، مقصدی برابر با آدرس بارگذاری داشته باشد.
    2. محاسبه‌ی آدرس مؤثر بارگذاری‌ها نسبت به همه‌ی ذخیره‌های قبلی به ترتیب برنامه انجام می‌شود.

این دو با هم تضمین می‌کنند که بارگذاری‌ای که از خانه‌ای می‌خواند که یک ذخیره‌ی قبلی در آن می‌نویسد، تا نوشته شدن داده صبر کند. بعضی پردازنده‌ها مقدار را مستقیماً از ذخیره به بارگذاری می‌رسانند. روش دیگر، پیش‌بینی تداخل است (جلسه‌ی ۸-۱۰).

## ۷. گمانه‌زنی برای اعداد صحیح و صدور چندگانه

کتاب سه نکته‌ی پایانی دارد:

- **فقط برای ممیز شناور نیست:** این روش‌ها به‌راحتی به ثبات‌ها و واحدهای صحیح گسترش می‌یابند.
- **برای برنامه‌های صحیح حتی مفیدتر است:** چون رفتار پرش در آن‌ها کمتر قابل پیش‌بینی است و بلوک‌های پایه کوتاه‌ترند.
- **با صدور چندگانه جذاب‌تر است:** با اجازه‌ی صدور و نهایی‌سازی چند دستور در هر سیکل. در پردازنده‌ی تک‌صدوری، روش‌های ساده‌تر (با کمک کامپایلر) احتمالاً ILP کافی داخل بلوک‌های پایه پیدا می‌کنند. جلسه‌ی بعد صدور چندگانه را می‌بیند.

## ۸. تمرین‌ها

<details>
<summary>تمرین ۱: ترتیب نهایی‌سازی</summary>

**صورت:** در وضعیت بخش ۱، اگر در هر سیکل یک دستور نهایی شود و هیچ پیش‌بینی غلطی نباشد، کدام سیکل‌ها چه چیزی را به حافظه یا ثبات‌ها می‌نویسند؟ (سیکل فعلی را ۰ بگیر.)

**جواب:** سیکل ۱: خانه‌ی ۳ (ذخیره، حافظه را می‌نویسد). سیکل ۲: خانه‌ی ۴ (R1 = R1 − 8). سیکل ۳: خانه‌ی ۵ (پرش درست بوده، فقط حذف می‌شود). سیکل ۴: خانه‌ی ۶ (F0). سیکل ۵: خانه‌ی ۷ (F4). سیکل ۶: خانه‌ی ۸ (حافظه). سیکل ۷: خانه‌ی ۹ (R1). سیکل ۸: خانه‌ی ۱۰.
</details>

<details>
<summary>تمرین ۲: پیش‌بینی غلط و ثبات F0</summary>

**صورت:** در وضعیت بخش ۱، اگر پرش خانه‌ی ۵ اشتباه پیش‌بینی شده باشد، بعد از بازیابی ثبات F0 چه مقداری دارد و فیلد وضعیتش چیست؟

**جواب:** F0 مقدار بارگذاری تکرار اول را دارد (خانه‌ی ۱ آن را نهایی کرده بود). بارگذاری تکرار دوم (خانه‌ی ۶) نهایی نشده و پاک می‌شود، پس هرگز F0 را نمی‌نویسد. با پاک شدن ROB، فیلد وضعیت ثبات‌ها هم پاک می‌شود و F0 دیگر «مشغول» نیست.
</details>

<details>
<summary>تمرین ۳: بارگذاری و ذخیره‌ی گمانه‌ای</summary>

**صورت:** در یک پردازنده‌ی گمانه‌زن، یک ذخیره بعد از یک پرش پیش‌بینی‌شده اجرا شده (آدرس و مقدارش آماده است). بعد یک بارگذاری به همان آدرس می‌آید. بارگذاری چه مقداری می‌گیرد؟ اگر پرش اشتباه پیش‌بینی شده باشد چه؟

**جواب:** ذخیره هنوز نهایی نشده، پس حافظه مقدار قدیمی را دارد. طبق محدودیت ۱، بارگذاری صبر می‌کند تا ذخیره نهایی شود (یا اگر ارسال ذخیره به بارگذاری وجود دارد، مقدار ذخیره را مستقیماً می‌گیرد). اگر پرش اشتباه بوده، هم ذخیره و هم بارگذاری (که بعد از پرش‌اند) پاک می‌شوند و حافظه هرگز عوض نمی‌شود. پس هیچ اثر غلطی باقی نمی‌ماند.
</details>
